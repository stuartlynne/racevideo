The last race of the year is the remaining opportunity to assess the current

operator may return it and revisit camera choice in February before spring road

## New app controls

Also see [motion/storage trial choices and quick review](MOTION_STORAGE_TRIAL.md).
**Motion / storage…** offers single-zone, three-strip, wide-road and entry/hold
behaviors. Keep Single as the baseline; draw zones to avoid flags/spectators and
compare recorded profiles. Storage proposals are explicitly non-destructive for
Sunday, so inspect their source-frame boundaries without losing originals.

The main review window now has **Confirm suggested bib**, **Previous bike / Next
bike** and an estimated count. New neural OCR builds a passage index; **Find bikes**
adds one to older captures without rerunning text recognition. Empty/incomplete OCR
is not evidence that there is only one bike. Capture 724's three passages are a
useful navigation check; manually marked 4/1 remain distinguishable on one frame.

Open **Camera…**, then use **Capture mode**. This lists the connected device's
discrete, advertised MJPEG modes, discovered with read-only V4L2 queries off Tk.
An advertised mode is a candidate for testing, not evidence of sustained output.

1. Stop the recorder using the main window. Let it finish saving the active event.
2. In Camera, select the ELP device and **Refresh modes**.
3. Choose **3840×2160 @ 60 fps**, if listed, and click **Use mode**.
4. Click **Start recorder**. Recheck manual exposure, gain and white balance:
   starting a different mode can reset camera controls.
5. Compare **Requested**, **Driver** and **Measured** fields. Warnings distinguish
   delivered dimensions/rate from a driver merely advertising 60 fps. Wait for
   the measurement window to fill, then run several minutes with actual movement.
6. Return to **3840×2160 @ 30 fps** using the same stop/select/start sequence.

Mode selection persists in the recording database for subsequent GUI starts.
Explicit CLI `--device`, `--width`, `--height` and `--fps` overrides take precedence.
There is no silent downgrade or automatic restart of an active recording.
Agent start/restart and camera reservations respect unfinished operator mode
edits and pending mode changes; close/apply the editor before agent reconfiguration.
The live preview remains independently limited to about 20 fps; preview refresh
rate is not capture rate. Motion analysis remains independently sampled.

The panel supports fractional advertised rates as well as 30/50/60 fps. Cameras
exposing only continuous/stepwise size ranges are not expanded into guessed modes.
This version continues to require MJPEG capture.

## Fair A/B comparison

Use the current 1–3 digit OCR rule and include single-, double- and triple-digit
plates. The old three-digit-only yield report excluded short bibs; see
`CONTEXTUAL_OCR.md`. Event/history hints are not yet connected to recognition.

Use the same placement, zoom/framing, focus, aperture, manual exposure time and
gain for the first comparison. Keep separate sessions at 4K/30 and 4K/60; do not
change everything at once. Then adjust exposure if necessary, retaining those
clips as a separately identifiable test. Check near and far sides of the road,
individual riders and overlapping groups. Check the lens/iris before the event.

Each new clip's `clip_details.metadata` includes:

- `camera_mode`: requested session configuration, delivered dimensions, negotiated
  rate, recent measured capture rate and bad-packet counter at trigger.
- Existing observed camera-control values and their observation timestamp, so
  shutter/gain comparisons do not rely solely on memory.
- `recording_metrics`: stored frame count, duration, average stored fps and largest
  inter-frame receipt gap. Review's clip heading also shows average saved fps.

Old footage is unchanged. Its saved fps can still be calculated from original
frame timestamps. Camera measurements describe received frames; they do not prove
unique sensor exposures, calibration of crossing times, or recognition accuracy.
Inspect consecutive moving frames for repeats and rolling-shutter deformation.

Check performance counters for bad JPEG packets, analysis overruns/backlog,
storage skips and insufficient pre-roll. A higher frame rate consumes more USB,
disk and compressed-buffer capacity. Do not call 60 fps successful solely because
the requested mode says 60. A short matching window is not a sustained-load test.

For OCR compare correct bib presence, wrong/ambiguous candidates and missed
visible plates against operator review. Candidate yield alone is not accuracy.
Tag/star representative good and bad evidence before date cleanup. There is no
automatic race scoring or CrossMgr write in this test.

## Speed changes the question

The operator clarified that current cyclocross passings are little above walking
speed. Road-race normal passings are approximately **40 km/h**; sprint finishes
are **50–60 km/h**. Sunday therefore tests low-speed usability, focus, lighting
and OCR, and does **not** qualify the camera for road finishes.

At a nominal 5 km/h versus 40/60 km/h, image motion is about 8/12 times faster
for the same geometry. Keeping similar motion blur would require exposures about
8/12 times shorter. For example, a satisfactory 1/500-second walking-speed image
could require roughly 1/4000 or 1/6000 second at those speeds, with correspondingly
greater light requirements. These are geometric estimates, not prescribed camera
settings; actual direction, magnification and acceptable digit blur matter.

At 60 km/h a rider travels about **56 cm between 30 fps frames**, versus **28 cm
at 60 fps**. More frames improve the chance of an unobscured view; exposure time
still determines smear within each frame. Global shutter removes row-to-row
geometric distortion but does not freeze motion during a long exposure.

If keeping this camera for spring, retain road-speed validation as an explicit
remaining requirement, using a controlled moving target or later race footage.
The earlier slow wheel tests do not establish road-speed performance.

Software tests cover actual Linux ioctl layouts, discrete MJPEG discovery,
stopped-only selection/persistence, rejection of unsupported modes, and warning
when requested 60 fps actually delivers 30 fps. A synthetic process-level recording
exercises separate dimension/measurement reports and persisted per-clip metrics.
Real Tk tests exercise mode selection and retained Apply feedback.

Read-only discovery found 105 MJPEG modes on the local Logitech C615. The ELP
was disconnected from zbook9 during this update, so its 4K/60 negotiation,
sustained throughput and image quality remain unverified on physical hardware.
No AMD experiments were performed, and the existing field-test evidence was not
rewritten. The all-frame OCR sweep remains an offline quality test; continuous
OCR within the laptop's two-core budget is a separate throughput requirement.

Validation: 85 local unit tests and 64 deployed-laptop unit tests pass. Real
Tk/Xvfb camera-panel tests pass on both hosts; HTTP MCP/reverse-GUI integration
passes with the new operator mode-edit guards. On zbook9, read-only enumeration
also found 12 MJPEG modes on its built-in camera; no images were captured from it.
